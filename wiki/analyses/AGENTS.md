# Analysis 页面写作规范

本文件适用于 `wiki/analyses/` 下的 LLM-authored analysis pages。

根目录 `AGENTS.md` 仍是最高层级规则。本文件只补充 analysis
页面的选题、写作、证据、审查和合作性表达要求，不允许削弱根规则对
`wiki/`、`raw/`、证据、隐私、安全、工具链、frontmatter、正文 provenance
和 source projection 的约束。

本文件面向 AI Agents。使用简体中文、专业口吻和可执行、可检查的短句。
保留必要的英文产品名、API 名、命令、文件路径、证据 `Type` token
和 `validation.body_contract` 值。

## 核心原则

Analysis 页面必须遵循 Grice 的 The Cooperative Principle：
在当前问题、当前证据和当前 wiki 维护阶段中，只提供有助于读者完成该问题判断的信息。

具体执行为四条准则：

1. **Quantity：信息量适中。**
   写足以支持结论的边界、证据、推理、限制和反例；不要为了显得公平、完整或知识丰富，
   加入与当前问题无关的旁枝、背景、候选方案、工具清单或泛泛优缺点。
2. **Quality：只写有把握且可追溯的主张。**
   技术事实必须回到一手来源、已投影 source page、源码、标准、release notes、
   API/CLI 文档、可复现实验或明确用户输入。不得把 AI 草稿、搜索摘要、印象、
   类比或术语相似性写成事实。
3. **Relation：始终贴合问题。**
   每个章节都必须服务于页面的核心问题。若某能力、产品或替代方案只在相邻问题中有价值，
   但不回答当前问题，应删除、降级为限制，或明确写成 out-of-scope。
4. **Manner：表达清楚且不可误导。**
   先给结论，再解释推理。避免含糊、双关、过度让步、口语化和会把读者引向错误问题的措辞。
   对相近概念使用同一抽象层级比较，必要时说明“这只在哪一层成立”。

## 页面边界

创建或更新 analysis 前，先写清楚：

1. 本页回答的一个核心问题是什么。
2. 读者是谁，读者要用本页做什么判断。
3. 本页不回答哪些相邻问题。
4. 哪些结论是技术事实，哪些是解释、推断、架构判断或决策建议。
5. 如果问题是选型、边界或决策，什么条件会改变结论。

不要把问题替换成更容易回答的相邻问题。
如果用户问的是“能否作为主 process manager”，不要改写成“能否作为调度层、执行层或 UI 层”。
如果用户问的是“能力是否等价”，不要只比较术语、品牌定位或营销分类。

## 分析页创建阈值

只在出现可复用 answer、comparison、decision、playbook 或 topic synthesis 时创建
analysis 页面。

优先更新已有 analysis。只有新问题边界有独立检索价值，且不能清晰并入已有页面时，
才创建新页面。

不要创建：

- 一页一个聊天回答；
- 一页一个 raw 草稿摘要；
- 一页一个产品优缺点清单；
- 一页一个松散工具目录；
- 一页一个临时 POC 想法；
- 只为容纳证据或显得完整而创建的页面。

## Body contract 选择

创建 analysis 页面时，必须选择最接近的 `validation.body_contract`：

| `validation.body_contract` | 使用场景 |
| --- | --- |
| `analysis-answer-memo` | 一个可复用问题需要一个综合答案。 |
| `analysis-topic-faq` | 一个有边界的话题包含多个并列问答。 |
| `analysis-decision-memo` | 记录选型、策略、范围、路线图、基线或权衡决策。 |
| `analysis-playbook-checklist` | 记录可重复执行的流程、排查路径、实验步骤或检查清单。 |

如果页面开始偏离所选 body contract，应重构、拆分或改为更合适的 contract。
不要用新增自定义字段绕过 body contract。

## 证据与 provenance

Analysis 页面中的技术事实必须可追溯。

使用证据时遵守以下规则：

1. AI 生成草稿只能作为线索、问题来源或用户认可边界；
   不能作为第三方产品能力、API 行为、版本特性、安全性质或选型结论的技术事实主证据。
2. 用户输入是一手需求、场景、约束、偏好和纠错证据；
   不是第三方技术事实的替代证据。
3. 外部证据进入 durable synthesis 时，若原始材料未保存在 `raw/`，必须为该具体外部来源创建或更新
   `wiki/sources/` source projection。
4. Source projection 必须是一页一个上游证据对象；
   不得把多个独立 URL、issue、release note、仓库文件或 raw 文件聚合成一页。
5. 不要因为 raw 文件存在就创建 source page。
   只有 durable analysis 需要该 source anchor 时才创建。
6. 正文最后必须有 `## 证据与限制`，并包含 `### 证据单元` 和 `### 支撑的主张` 两张表。
7. 支撑主张表必须覆盖页面中的主要结论、决策、限制和条件。
   高风险或决策敏感主张必须映射到具体证据和限制。

## 机制优先

分析概念、产品或机制时，先比较能力和运行语义，再使用术语。

至少检查：

- 基本对象是什么；
- 谁解释控制规范；
- 哪些状态被持久化；
- 外部事件进入哪个对象；
- 故障后恢复什么；
- 副作用边界在哪里；
- 哪些行为由运行时保证，哪些必须由业务设计补足；
- 哪些结论依赖版本、部署方式、规模或组织约束。

名词相同不代表能力相同，名词不同也不代表能力不同。
若只在某个轴上相似，必须写清“只在该轴上相似”。

## 替代方案与反方

只有当当前问题涉及真实选择、存在可行替代方案，或证据中有实质反方解释时，
才展开替代方案。

处理替代方案时：

1. 公平描述它在当前问题中的能力，不虚构弱点。
2. 不把相邻问题中的优势写成当前问题的答案。
3. 不用“也可以做某些外围工作”模糊“是否满足核心职责”。
4. 若替代方案成立需要把核心职责交给外部系统，必须明确写出：
   外部系统才承担该职责，替代方案只是适配层、执行层或展示层。
5. 对不属于当前问题的优点，只能作为 out-of-scope 条件或重新审视触发条件。

## 结论表达

Analysis 页面必须给出明确结论。

结论可以是条件化结论，但不能用“取决于情况”“还需进一步调研”“各有优劣”
替代判断。

如果关键证据仍可查，先补查一手来源。
如果受权限、任务边界、成本、时间、环境或用户输入阻断，写清：

- 缺口是什么；
- 为什么当前不能补齐；
- 该缺口会影响哪些主张；
- 后续如何验证。

不要把弱证据写成强结论。
也不要因为无法给出采购结论，就回避可由当前证据支持的技术语义判断。

## 结构要求

分析页应先让读者知道答案，再展示推理。

推荐结构：

1. 问题、决策或答案。
2. 范围和非目标。
3. 理由或机制模型。
4. 替代方案和限制。
5. 后果、风险、重新审视条件或 POC 边界。
6. `## 证据与限制`。

可以使用表格对齐维度，但表格不能替代正文推理。
每张表都应回答一个明确问题；不要用表格堆砌产品、工具或术语。

## Grice 检查清单

提交 analysis 页面前，逐项检查：

- 当前结论是否直接回答页面标题和核心问题。
- 是否存在“正确但不相关”的段落。
- 是否存在会让读者误以为 scope 已改变的让步、补充或替代方案。
- 是否把相邻角色、外围层、执行层、UI 层或数据层写成了当前问题的答案。
- 是否把 AI 草稿、搜索摘要或术语相似性当成了技术事实。
- 是否对每个高风险主张给出证据和限制。
- 是否明确区分事实、解释、推断和判断。
- 是否写清版本、时间、环境、规模和组织约束。
- 是否给出可验证结论，而不是泛泛优缺点。
- 是否删除了不服务于当前问题的工具清单和背景材料。

## 审查与迭代

对高风险、决策敏感、将被复用、将进入 wiki 入口、或用户明确要求的 analysis，
必须进行独立对抗审查。

审查重点：

- 问题是否被替换成相邻问题；
- 是否违反 Grice 的 Quantity、Quality、Relation 或 Manner；
- 术语是否替代理解；
- 相近概念是否混淆；
- 替代方案是否被低估或被无关优势抬高；
- 证据是否被夸大；
- 页面边界是否清楚；
- 结论是否可验证；
- provenance 是否足以审计。

只对阻断性问题持续迭代。
当审查意见指出 scope 偏移或误导读者时，优先修正文中问题，而不是只在限制部分补一句免责声明。

## 与日志和校验的关系

Analysis 页面的 durable 语义变更必须追加 `wiki/log.jsonl` 事件。
纯 `AGENTS.md` 指令文件变更不是 analysis 页面语义变更，不要为了本文件自身修改而写 wiki log。

完成 analysis 页面或 source projection 变更后，运行：

```bash
mise run wiki-check
```

不得绕过 `mise` 使用全局项目工具。
